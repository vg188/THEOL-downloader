# 2.5.4 下载完整性验收

**结论：受控样本及少量真实课程原文件均已核对名称、类型和保存字节；完整书签 UI 的真实 ZIP 下载也已通过。** 不将自动化通过等同于所有课程、文件和权限状态均可“完美运行”。

验证日期：2026-10-08（Asia/Shanghai）。Chrome 154.0.8037.98，Windows，Node.js 24.19.0。

## 本轮修复

| 原问题 | 当前行为 |
| --- | --- |
| ZIP 文件头不能区分 PPTX、DOCX、XLSX | 完整响应检查主文档部件、类型声明、根关系、本地／中央目录和条目 CRC |
| OLE 魔数不能区分 PPT、DOC、XLS | 完整响应检查复合文件 FAT／MiniFAT、目录／流长度及根文档流 |
| 截断 PDF、部分 HTTP 响应可能被当作成功 | 检查 PDF 尾部与交叉引用；拒绝不完整响应、错误 Range 和声明长度不符 |
| 只相信预览名，没有核对响应名 | 解码 Content-Disposition 的 UTF-8／旧式编码，与预览原名比较；冲突时停止而非改后缀 |
| 合法连续空格被清理；深目录只限制单段长度 | 保留合法空格；同时约束路径段和总路径长度；保留后缀并提供实际保存路径 |
| 原生完成记录没有核对最终文件 | 对照 Chrome 的名称、路径和可知大小，记录实际路径；异常不记成功 |
| 预检后再次 GET 可能得到另一份响应 | 书签小文件直接保存同一份完整响应；原生请求在有强 ETag 时携带 If-Match |
| 批量完成提示覆盖了单项错误 | 面板保留失败文件及原因；跳过项不占用未使用的 ZIP 重名序号 |
| 原站空包容易被误认为下载丢失了内容 | 保留合法原始文件，并显示“原 ZIP 为空（0 个条目）” |
| Chrome 一项查询失败阻塞整个队列 | 隔离查询错误，保留原下载并定期对账，不重复提交 |
| 没有单元或主动跳过单元被计为失败 | 改为说明原因的正常空状态 |

## 实际 Chrome 落盘结果

测试使用独立临时配置和本机回环服务器，不复用已登录的学校会话。原生下载不受普通页面路由拦截可靠控制，因此测试将学校域名显式映射到回环服务器；其他仅使用页面拦截的用例禁止该域名的真实 DNS 解析。

### 扩展：13 个成功样本、5 个异常场景

成功样本包含 PDF、DOC/DOCX、PPT/PPTX、XLS/XLSX、PNG、JPEG 九种格式，另测试 Windows 保留名、同名但不同内容的 PDF、超长中文／Emoji 名称，以及原始空 ZIP 的明确警示。

每个成功样本都核对了：

1. 选择的资源 ID 与响应来源。
2. 原文件名、大小写后缀及实际保存路径。
3. 磁盘文件大小、可识别的格式结构。
4. 磁盘文件与对应源样本的 SHA-256 完全一致。

真实传输并发不超过 2。关闭面板并终止后台 Service Worker 后，恢复的任务继续完成，没有重复原生下载。同名文件分别保存，没有覆盖。活动队列注册后台定期对账，终态队列清除唤醒；单项临时查询失败不再阻塞其他项或误取消下载。

以下情况均未误报完成：响应名不同、PPTX 地址返回 DOCX、预检后版本变化（HTTP 412）、传输截断、返回登录页。异常文件可能已进入 Chrome 下载目录，程序不会自动删除用户磁盘文件。

### 书签：ZIP 和逐个下载

- 真实下载一个含 PPT、PDF、DOCX 的 ZIP，解压后核对三个路径和原始字节哈希。
- 另用嵌套课程目录／单元用例核对三个 PDF 的归档路径和不同源内容。
- 逐个下载一个大于 64 KiB 的 PPT 和一个小于 64 KiB 的 DOCX，核对浏览器文件名和落盘哈希。
- 小 DOCX 只读取一次，保存同一份已校验响应；大 PPT 仍为一次预检加一次原生下载。
- 浏览器测试显式允许模拟站点的多文件下载；真实 Chrome 首次使用时仍可能要求用户允许。

### 样本可以独立打开

样本位于 tests/fixtures/downloads/。除了本项目自己的检查，还使用了独立工具：

- PyMuPDF 打开 PDF、提取正文并渲染页面。
- python-docx、python-pptx、openpyxl 核对段落、幻灯片标题和单元格。
- Microsoft Word、PowerPoint、Excel 只读打开旧格式，核对相同正文／单元格。
- Pillow 解码 PNG／JPEG 并核对尺寸。

因此不是用不完整的文件头来“证明”下载成功。源文件能打开，下载文件又与源文件逐字节相同。

## 校验边界

| 路径／格式 | 能确认的内容 | 不能据此承诺的内容 |
| --- | --- | --- |
| ZIP 模式 | 已读取完整响应、名称／长度核对、支持格式的结构及 ZIP CRC，原字节进入外层 ZIP | 上传源文件自身的语义正确性；浏览器最终是否保留了下载文件 |
| 扩展原生下载 | 最多 64 KiB 预检、完成事件、最终名称和可知大小；有强 ETag 时限制版本 | 不读取磁盘正文，不对最终文件逐字节认证；缺少 ETag 时两次响应可能不同 |
| 书签小文件逐个保存 | 完整读取的小文件复用同一响应，不再请求一次 | 书签不能查询 Chrome 下载完成状态 |
| 书签大文件原生下载 | 预检、触发请求和逐项错误提示 | 完整类型／内容校验、实际落盘完成及目录保留 |
| PDF | 头部、尾部、交叉引用结构 | 所有页面／字体／嵌入内容的语义或渲染正确性 |
| Office／ZIP | 支持的容器结构；普通 store／deflate 条目 CRC | 密码保护文档内部类型或内容；任意第三方格式兼容性 |
| ZIP64／超限内容 | 明确停止完整校验，不静默放行 | 当前不能提供完整 ZIP64 校验；可在平台手动下载核对 |
| RAR／7z／其他格式 | 按实现提供签名或有限容器检查，未知格式不标为完整验证 | 不等于完整解压验证或病毒扫描 |

解压校验限制单个条目 256 MiB、累计 512 MiB、最多 20,000 条；Office 关键结构部件另有 8 MiB 上限。这些限制不同于用户设置的外层 ZIP 包体预算。

路径清理不是完全不改名：非法字符、保留名、超长路径和重名需要调整。程序保留可用后缀并显示实际路径，不把 PPT 自动改名成 PPTX。整个相对路径限制为 200 字符，但很长的下载根目录仍可能受操作系统限制。

## 真实课程下载续验

初始课程的 17 个单元、4 个目录、50 条资源仍然没有下载入口，未绕过此限制。随后通过用户已登录平台的课程列表进入其他课程，只使用页面明确显示的“下载”链接。

| 真实样本 | 观察到的原文件 | 结果 |
| --- | --- | --- |
| PDF 讲义 | 4,564,807 字节，29 页 | 原站下载可打开；项目 ZIP 内字节完全一致 |
| PPTX 讲义 | 147,377 字节，83 个 ZIP 条目，14 张幻灯片 | 原站下载、正式 ZIP 模块、完整书签 UI 的三份原始文件字节完全一致 |
| 原站 ZIP | 22 字节，0 个条目 | 原站文件本身为空；程序保留该文件并提示，不伪造缺失内容 |

PDF 用 PyMuPDF 打开、提取正文并渲染首页；PPTX 用 python-pptx 打开并核对 14 张幻灯片，没有隐藏幻灯片标记。平台的转换预览只显示 13 页，不能用预览页数判断原文件内容，也不应下载转换图片冒充原始 PPTX。

真实服务器忽略 Range，返回 HTTP 200，带 Content-Length；PPTX 使用 application/octet-stream，Content-Disposition 采用带普通空格的 UTF-8 百分号编码，未提供 ETag。这些响应已通过正式预检和完整文件读取。没有 ETag 时，程序不会声称可保证两次网络响应永远一致，本次通过独立下载和哈希对照确认。

完整书签界面在一个 newpage 模板课程中扫描出 76 条课程资源，跳过全部单元后未报读取失败；仅选择一份 PPTX，生成课程命名的 ZIP，目录和原文件名均对应。没有整门课批量下载。原文件、真实响应元信息和截图均留在 Git 忽略的本地目录，没有把课程正文或账号信息放入测试夹具。

仍需验证的范围：扩展直接接入真实登录课程的原生队列、真实登录过期／权限变化、其他文件格式，以及尚未遇到的分页结构。当前不能承诺所有课程和所有源文件都完好。
